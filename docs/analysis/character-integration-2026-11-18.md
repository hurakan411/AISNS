# 固定キャラクター＋投稿ごとの着眼点：組み込みと検証

## 実装

- 30種類から、その生成に必要なキャラクター定義だけを送る。一般AIの同一投稿内では重複を避け、30人を超えるバズ投稿では候補を使い切った後に再利用する。
- 通常投稿と返信スレッドでキャラクター指示とリアクションの分担を併用。キャラは口調・普段の注目傾向、リアクションは今回の返信の役割。後者がキャラの丁寧さや記号方針を上書きしないようにした。
- 通常返信の役割は従来同様に生成ごとにシャッフルする。全員に同じ助言や質問をさせない指示を維持。キャラのための追加API呼び出しはない。
- 絵文字タイプ4人、顔文字タイプ2人、残りは文章中心。落ち込みへの明るい記号・祝福・ふざけた記号を抑える。記号方針は各定義に明示する。
- 新規の常連は、登録元の返信のcharacter_idをiOSに固定保存。通常投稿・返信スレッド・常連の総評の着眼点で共有する。
- 設定前の既存常連はfollower_idのSHA-256から同じIDを引き当てる。新版アプリはサーバーから返ったIDを一度だけ保存し、以降は上書きしない。
- 会話の記憶更新が省略された応答でも、返信に返ったキャラIDは常連へ保存する。キャラを含むReplyとRegularFollowerの旧保存データ互換性を維持した。
- 特定の一般AIへのユーザー返信でも、そのAIのcharacter_idを渡して同じキャラを引き継ぐ。スレッドに参加する他AIのIDも渡す。
- リクエストの追加フィールドは省略可能。既存クライアントは新しいレスポンス項目を無視でき、新版クライアントも旧サーバーからのIDなし応答を読める。DBのDDL変更はない。

## 検証結果

- Python単体テスト53件成功（日英・投稿／スレッド・旧リクエスト・バズ32返信・常連ID優先・選択した定義のみ送信・重複回避など）。
- Swiftの会話保存テスト成功：旧常連データ、キャラIDの一度だけの保存、JSON往復、記憶10件と総評日時の互換性。
- Swiftの返信保存テスト成功：旧ReplyデータとキャラIDつきReplyのJSON往復。
- iOSの汎用端末向けDebugビルド成功。実機が接続されていなかったため、今回の実装のインストール・端末上の操作確認は未実施。
- Lunaを実際に呼ぶローカルFastAPIテスト7ケース成功：日本語通常投稿、落ち込み、画像、英語スレッド、同じ常連3人での2投稿、常連スレッド。
- その後、記憶の参照範囲と記号方針を明確化し、日本語落ち込み・常連投稿・常連スレッドの3ケースを再生成して成功。
- すべて合成入力。実ユーザーのデータ・DB・Renderには書き込んでいない。各ケースのAPI呼び出しは1回。

## 実生成から確認できたことと限界

常連「ゆき＝v1-03」「みく＝v1-13」「れん＝v1-09」は通常投稿とスレッドで同じIDを維持した。ゆきに🙌、みくに(´▽`)や(^^)、れんに記号なしの反応が見られた。記号は毎回必須にはしていない。

最初の生成では一般AIが常連の記憶にだけある「声に出して練習した」という細部を使った例や、記号なしキャラに絵文字が付いた例があった。このため参照範囲と記号ルールを追加した。再確認の小規模サンプルでは同じ逸脱は見当たらなかったが、将来の全返信で守られる保証ではない。

「ほっとした」という短い報告に複数人が似た安心感を返す例は残る。キャラIDの固定・役割指示の共存を検証したもので、キャラらしさや重複の完全解消・継続率向上を保証するものではない。
